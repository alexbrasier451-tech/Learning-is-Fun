## Produced outputs/interfaces

**Concrete reward DTO contract.** Keep these reward-domain types in `src/rewards/contracts.ts`; WP03 owns canonical equivalence, response/evaluation and learning facts, WP04 owns commands/state transitions. UI never sends awarded points or creates its own eligible selection. DEC-030 accepts the reconciliation and per-profile personal-record refinement below; DEC-032 accepts the imported EligibilityResult for the committed activity projection. This child remains the sole exact definition source for its producer and consuming adapters.

| DTO / function | Input/output / invariant |
|---|---|
| `EligibilityResult` | Readonly classification output `{ kind: "eligible-first" / "eligible-review" / "resume-existing" / "practice-only", reason }`. Reasons are respectively `first-encounter`, `selected-due-review`, `unfinished-opportunity`, or one of `same-week-used` / `child-practice` / `not-due` / `unfinished-free-practice` / `familiar-repeat`. WP05-02A produces it; WP04 stores the latest selection/first-Check decision and exposes it read-only in committed activity projections. It describes policy classification, not an earned delta or a promise that a weekly slot is available. |
| `RewardSelectionFacts` | Persisted `{ profileId, canonicalQuestionId, encounterId, selectionReason: story / adaptive / due-review / child-practice, candidate: first-encounter / later-week-due-review / none, dueLocalDate?, previousSuccessWeek?, band }`, adapted from WP03 selection inside WP04. Opportunity ordinal belongs to the allocated reward opportunity, not WP03 selection. Due date alone is insufficient: WP03 must select review and its earning week must be later than previous success. WP04-04A owns the explicit learning-reason→reward-reason mapping. |
| `RewardOpportunity` | `{ opportunityId, profileId, canonicalQuestionId, ordinal, selectionFacts, earningWeek: WeekKey or null, slot: 1..30 or null, validChecks, answerHintUsed, firstSuccessWeek?, firstSuccessLocalDate?, components }`. A pre-Check selected opportunity has null week/slot and persists assistance; first valid Check binds the week and eligibility/slot. Resume retains the same opportunity ID/ordinal. |
| Identity encoding | `opportunityId` is the durable reward token allocated by WP04 and retained with the stable encounter token. After first Check its unique reward key is `[profileId, canonicalQuestionId, earningWeek]`, encoded without delimiter ambiguity. Canonical ID never incorporates the week. `submissionId` is separate; cumulative `checkSequence` prevents replay/out-of-order attempts. DEC-024 episode ordinals distinguish learning completions within this same unresolved encounter/opportunity; they never enter the reward key or reset validChecks. |
| `RewardReceipt` / `ScoreDelta` | Receipt key `{ opportunityId, component: answer / independent-success / supported-success }`, corresponding amounts 5/15/5 and mutually exclusive success flags. Quest receipt key `{ profileId, questId }` is lifetime-only +20. `ScoreDelta` is `{ lifetimeDelta, competitiveDelta, consumedSlot?, newReceiptKeys, newEntitlementIds }`, computed internally, never accepted from UI. |
| `applyCheckRewards` | Input stored reward/encounter state, valid WP03 evaluation, recorded assistance/selection and reconciled calendar; output next reward state plus delta. Invalid response produces no attempt/award. An already-applied sequence produces no delta; success after week closure updates lifetime only. No storage/audio/DOM/network operation. |
| `CanonicalRewardTrack` | `{ lastAllocatedOrdinal, completedThroughOrdinal, closedAwardTotal, lastSuccessWeek?, lastSuccessLocalDate?, freePractice: { latestWeek?, validChecks, answerHintUsed, unfinishedEncounterId? }, currentOpportunity?, recentCompletedOpportunity? }`. A new rewardable review increases ordinal, not canonical ID. Retain unfinished free-practice attempts/assistance through route/week changes until success; previous success and current-week contamination constrain later eligibility independently of reward totals. |
| Compaction / idempotency | Retain full unfinished opportunity/component/submission facts, current-week slot/receipt facts and the latest completed outcome. Older completed opportunities fold their exact lifetime contribution into `closedAwardTotal` and advance `completedThroughOrdinal`; ordinals at or below the mark can never reopen. Skill summaries/recent evidence stay WP03-owned. Retained matching submissions return already-applied/current state; removed encounter IDs are rejected as expired. Neither route regenerates a learning observation or celebration. Validate that no imported open opportunity lies below its completion mark. |
| `CompetitionState` / `ClosedWeekResult` | `{ timezone: "Europe/London", latestOpenedWeek, currentScores/slots, archives, policyVersion }`; closed results have week/local-date keys, original positive ranks/medals and nickname/avatar snapshots. Personal best/cumulative medals live per profile independently of the 52-archive window. Once a week is closed, it cannot be reopened or awarded again; deleting entries preserves survivor ranks and marks omission. |
| `LeaderboardReadModel` | `{ localScopeLabel, activeWeek, activeWeekLabel, timezone, clockNotice?, profiles: [{ profileId, nickname, avatarId, competitivePoints, lifetimePoints, usedSlots, rank: number or null }], recentClosedResults, personalRecordsByProfile }`. Records hold each profile's personalBest and cumulativeMedals; they are not a household scalar. WP05's pure selector builds this from committed data and WP04 exposes it. Hall/Festival never mutate totals or grant medals. |

One current opportunity per canonical task is enough for the bounded policy: an unfinished Check path survives route/week changes, while completed work can have a new selected review later. Repeated free practice still records WP03 observations but opens no reward opportunity; its current-week first-attempt/assistance facts prevent route switching from manufacturing eligibility. WP04 retains submission sequence high-water/tombstones together with these reward tracks so compaction cannot allow a second learning or score application. Reward selection at first Check revalidates stored facts against current success/free-practice/week state; a stale selection cannot claim another opportunity for a week already used.

**Exact producer ports.** Reward contracts contain plain data and function-input/result types only. ProfileId/QuestId are opaque bounded strings here, so the early module never imports later state/experience. Import canonical/skill/band/evaluation types from WP03. `CalendarContext = { observedLocalDate: LocalDate, activeWeek: WeekKey, clockRollback: boolean }`. `ReconciliationInput = { competition: CompetitionState, profiles: readonly CompetitionProfile[] }`, where CompetitionProfile is `{ profileId, nickname, avatarId, lifetimePoints, personalRecords }`. `ReconciliationResult = { nextCompetition, nextPersonalRecordsByProfile, context, closedWeekChanges }`; including personal records is mandatory so closure can atomically award medals/update bests outside the 52-week archive. `ClosedWeekChange = { week, result }` is presentation data, never another award request. The registry, not state, owns these types. WP04 applies returned records and competition together.

`CompetitionState.currentScores` maps profile IDs to nonnegative totals; `currentSlots` maps profile IDs to ordered `{ slot, opportunityId, canonicalQuestionId, points }` entries (slot 1–30, unique). A current score equals its slot point sum; lifetime-only awards never appear here. Zero-score/new profiles may be absent from maps and read as zero. `ClosedWeekResult = { week, timezone, policyVersion, entries: [{ profileId, nickname, avatarId, points, rank, medal }], omittedDeletedProfiles: boolean }`; entries contain positive scores only, medal is gold/silver/bronze/null. `PersonalRecords = { best: { points, week } or null, medals: { gold, silver, bronze } }`; equal best retains original week. Scores/counts/ordinals are safe integers. `latestOpenedWeek: WeekKey or null` supports a first-run empty competition without inventing prior weeks.

`RewardState = { lifetimePoints, tracksByCanonical, questReceipts, entitlementIds }`; compact track totals plus retained opportunity components plus +20 per quest receipt must equal lifetimePoints. Validators never add a compacted component twice. `RewardCheckInput` supplies profile/encounter/opportunity identity, stored track and reward state, a judged WP03 result, cumulative valid Check/assistance/selection facts, competition and CalendarContext. `RewardCheckResult = { nextRewards, nextCompetition, delta: ScoreDelta }`. Slot consumption records its actual number; null means noncompetitive/capped/unbound, distinguished by eligibility reason. No learning episode ordinal is used for once-only reward receipt identity.

**Early calendar output.** `CompetitionClock = { nowEpochMs(): number }`, normally Date.now. `localDateAt(epochMs: number): LocalDate`, `weekKeyFor(date: LocalDate): WeekKey`, `addCalendarDays(date: LocalDate, days: integer): LocalDate` validate inputs and return date-only results; failure is a typed invalid-date/unsupported-zone error, not a fallback date. localDateAt uses Intl.DateTimeFormat en-GB with explicit Europe/London, gregory/latn and year/month/day formatToParts. LocalDate and WeekKey are validated YYYY-MM-DD; WeekKey is Monday's local date. UTC is only a neutral date-only arithmetic carrier, never a London midnight instant. Do not parse localized display text, use implicit browser zone or add elapsed 7×24h across DST. WP03's three/seven-day adapter uses these helpers; all functions except the injected clock are pure.

Stage 6 reuse: native [Intl formatToParts](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/DateTimeFormat/formatToParts), original small date helper, no runtime dependency. [Luxon](https://github.com/moment/luxon), [MIT licence](https://github.com/moment/luxon/blob/master/LICENSE.md), was assessed and rejected: one fixed zone/date arithmetic does not need it. Reassess only for material new requirements. No remote clock, trusted time service or Temporal polyfill.

Date output is identical across browser/device timezones; Monday week keys, leap/month/year boundaries and three/seven calendar-day adds across both DST periods are correct. Downstream contracts can express closed-week/rollback/late-success state without inventing a server clock.

Typecheck the exact ReconciliationInput/Result above, including personal records, with `reconcileCompetitionWeek(input, nowEpochMs): ReconciliationResult` reserved for WP05-03A implementation. It imports no SaveDataV1/controller and carries one observed time context for learning/rewards. Do not export a successful no-op closure.

Representative date fixtures include London Sunday/Monday, summer and winter instants under two different host timezones, invalid dates, leap/month/year boundaries, and three/seven calendar-day additions spanning both DST changes. The same epoch must yield the same London date/week regardless of host zone; unsupported explicit-zone handling is a reported failure, not host-zone substitution.
