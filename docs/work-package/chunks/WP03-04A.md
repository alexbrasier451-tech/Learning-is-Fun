Inputs are readonly, outputs replace changed records and preserve unaffected skills. Each skill/band keeps aggregate valid-Check/help/success counts, the last four completed episode facts, last distinct successful canonical IDs needed by that window, and review dates/outcomes; keep one active episode accumulator per retained encounter rather than duplicate a complete event log. WP04 retains durable deduplication/tombstones and supplies authoritative facts, not a second policy in the UI.

`resolveBindingIntent(input: { route: LearningRouteIntent, milestone: 'M1' | 'M2', bindings: readonly QuestActivityBinding[], catalogue: readonly TaskDefinition[], accessibleQuestIds: readonly string[], completedStoryBindingIds: readonly ActivityBindingId[] }): BindingResolution` is a pure export from `select.ts`. Apply the exact route/role/source rules owned in [WP03-01A](WP03-01A.md). WP04 validates its own command and supplies committed world/catalogue facts; this function allocates no encounter and imports no state/experience module. Its unavailable result creates no learning observation or reward opportunity. The ordered binding array, not an encounter history scan, chooses the next incomplete required beat.

`SelectionRequest` explicitly names `catalogue, intent: ResolvedSelectionIntent, evidence, activeEncounter, canonicalHistory, calendar, suppressDueReviewForVisit`. A fresh intent is exclusively the resolver's successful output; for resume WP04 reconstructs it from the retained encounter's immutable binding provenance and canonical descriptor, revalidating them against the same current catalogue. `suppressDueReviewForVisit` is the boolean owned by WP04-01A OpenEncounter, supplied by the UI for the current visit; it is not a score or ability fact. `canonicalHistory` is the learning-owned projection of pending attempts/help, prior successes and WP05 eligibility constraints supplied by WP04. Calendar fields are those in WP03-01A; WP05 owns their construction.

`SelectionResult.status` is `selected | no-suitable-task`; selected fields are `canonicalQuestionId, band, reason, bindingProvenance: ActivityBindingProvenance | null, familiar, reviewReference, resumeEncounterId, rewardCandidate, unavailableSuggestion`. The selected task must belong to the resolved binding's pool when bound; provenance is copied only from the validated intent or the unchanged retained encounter on resume, not the command/UI. Null means absent, never an invented task/ID. `rewardCandidate` is `first-encounter | later-week-due-review | none`; it remains advisory to WP05. WP04 persists the selected bindingProvenance with the task before display and uses it for later Check/finish/resume. Changing navigation cannot change it. WP04-04A owns the consuming translation to RewardSelectionFacts; transfer maps to adaptive for rewards while retaining transfer as the educational reason. Resume retains the original reason and all cumulative attempts/help.

Optional-transfer provenance survives compaction without a new history structure: the M1 transfer row references an immutable singleton story source, permanent completedStoryBindingIds proves that source succeeded, and source.taskIds[0] supplies previousCanonicalQuestionId. The selector excludes that canonical ID. Its current transfer encounter then saves the normal binding provenance/descriptor. Neither reopening a compacted source encounter nor accepting a previous-task ID from UI is permitted. Other optional skill work is a revisit, not a newly invented source-dependent transfer.

If an unresolved canonical encounter already exists under different binding provenance, return that encounter as the resume target with its original provenance/reason; do not attach a requested story or optional binding to it. UI identifies the resumed work from committed projection. Once it succeeds, a subsequent fresh request can select a required story encounter; canonical reward/history rules still prevent a renewed bonus. This is the existing unfinished-canonical continuation rule, not a second reward opportunity or a mutable completion claim.

## Exact scope

**Evidence ownership.** Record per skill/band encounters, first-Check correctness, attempts until success, assistance/context, justified mistake observations, later distinct-task success and dated review. A wrong response is an observation, not diagnosis. Update only primary assessed objectives with suitable evidence; merchant M04 success is mixed-task, not independent E08 reading/M02 mastery. Routine narration/accessibility is not mathematical struggle. Assessed-text read-aloud is listening-supported comprehension, not independent reading; access/progress/ordinary points continue.

Apply WP03-01A's accepted DEC-025 observation fields: a wrong `check` uses episodeCheckIndex/encounterCheckIndex to update attempts/current episode but not the completed window; a correct `check` appends one succeeded episode; `finished-unsuccessfully` appends one Check-bearing unsuccessful episode without carrying a Check index or incrementing Check count. Suspension produces no observation. Resumption after unsuccessful finish starts the next episode under the retained encounter, with inherited attempts/help; eventual correctness is retry/supported success, not independent first success. Zero-Check finish has no observation. Learning completion cannot request reward completion/compaction. Summary counts distinguish valid Checks from completed episodes so a finish command cannot inflate attempts. A factual later success on a distinct task is retained even when the prior task was helped.

Selection order is deterministic within the resolved intent: resume retained work without rebinding; for a story binding use its singleton anchor or choose a suitable band from its own M2 pool; for optional transfer exclude the source anchor and stay within its transfer pool; for revisit stay within its own pool; for unbound suggested practice optionally offer the oldest unsuppressed due review. Then choose the suggested available band, unseen before familiar, stable canonical order as final tie-break. Child-easier/repeat routes keep their explicit noncompetitive intent. Never expand a bound request to unrelated content to fill a missing band. The UI must offer the due-review skip, then re-request with suppressDueReviewForVisit=true until the next visit. Do not replace an explicit fixed anchor or force a review. A supplied resume target with no valid retained descriptor returns recoverable no-suitable-task. Ordinary selection never scans undelivered M2 definitions into availability. One incomplete or wrong encounter cannot displace other skills' evidence.

Independent success: first valid Check correct, no answer-relevant hint/worked support and evidence suitable for that objective. Hinted/retry/guided completion still records success and can restore the world, without rewriting earlier independent status. Draft/hint events are separate durable facts, never synthetic Checks. Per-submission idempotence/stale/expired checks and compacted encounter high-water marks belong to WP04; this pure reducer consumes validated new observations once and must not infer a new observation from a compacted receipt.

**Bands and prerequisite suggestions.** support/core/stretch are authored demand per objective, not age, numeric difficulty multipliers or equivalent ability across subjects. Start unobserved skills at core when available except fixed introductory story anchors; otherwise offer honest introductory fallback. Suggest next available band after three independent successes on three distinct canonical tasks among the last four completed Check-bearing encounters in the current band. Retries/replay/familiar repeat cannot supply distinct identities; individual retries are not four encounters. Unchecked departure/navigation does not close unsuccessful work. Two consecutive encounters needing answer help or ending unsuccessfully suggest support/approved prerequisite. Lowest-band support is hints/worked support or an actually delivered prerequisite; unavailable content gets a suggestion, not an empty task. Highest/unavailable next band retains distinct practice/review and “harder practice not available yet”. Change no other skill or world progress. Child-requested easier practice is always available, labelled child-easier/noncompetitive by WP05 policy.

**Calendar review.** First independent success at each band schedules +3 calendar days; independent review success schedules +7; supported/unsuccessful review schedules support and +3. Use WP05 addCalendarDays/context in Europe/London, not 72/168 elapsed hours or browser-zone parsing. Missing days cause due suggestions without overdue punishment. Prefer unseen suitable tasks; familiar-item review is labelled and not transfer evidence. Offer at most one due review before return to the chosen adventure, with skip; skip produces no Check/failure, keeps due date and suppresses repeat prompting during that visit. Visit suppression is an explicit selection input, not durable mastery state.

**Identity/history and reward candidates.** Canonical identity never changes with week/release/seed/skin. First encounter or educationally due review in a later competition week than that canonical's actual previous success can return a candidate. Same-week due review is useful nonrewardable practice. Calendar rollover alone opens nothing. Resume unfinished encounter/opportunity with all original attempts/help, even across weeks; first valid Check binds earning week in WP04/WP05. Free-practice Checks/assistance are persisted and prevent route-switching into a fresh first attempt that week; pending free practice cannot be washed clean by route/week changes. Delayed success keeps original earning week, and any later review waits for a later week than actual success. Selection never allocates IDs, reserves competitive slots or calculates points. Legitimate later due review gets its own encounter/first Check but retains old learning/receipt history.

**Finite pools/summaries.** M1 policy operates on M01/M04/E06 pools; contextual skills have no fabricated mastery. Exhaustion yields labelled repeat practice, learning and world access; the 30 weekly cap is not a bank quota or entitlement. M2 data activates 20 skills using the same policy. summaries expose counts/recent dated outcomes, supported versus independent/retry/later-distinct success, current/available band, review due/latest result, familiar labels and missing evidence. Labels may say practising/ready for harder work/review due; never calibrated mastery percentages.

Assistance semantics remain the same for text/spoken help. Routine control/instruction narration, muting, volume, Stop and replaying neutral instructions change no attempts/eligibility. Persisted answer-hint/read-aloud facts are supplied before help is shown; WP02 honours Silence all and safe punctuation narration. This module emits categories, not playback.

## Acceptance criteria

1. Controlled histories demonstrate three distinct successes among four completed encounters, replay/retries insufficient, two struggles/support, per-skill isolation and available/unavailable band/prerequisite fallbacks.
2. +3/+7/+3 review dates remain calendar dates across Monday/DST/missed days; skip keeps due and suppresses visit re-prompt without failure.
3. Same-week familiar review is practice; later-week educational review returns a candidate with unchanged canonical ID and familiar evidence, never transfer. Pending hints/attempts/free-practice contamination/old-week delayed success cannot reset.
4. Suitable independent versus supported/listening/mixed evidence is explicit in summaries; guided success preserves progress but not independent reading evidence. No ability percent, quest lock or score allocation.
5. Immutable pure outputs serialize; invalid/unavailable/incomplete events do not become attempts. WP04's later integrated reload/duplicate/failure cases must preserve these facts.

6. A compact acceptance table names canonical tasks A/B/C/D explicitly: independent A/B/C among four completed encounters suggests the next available band; A/A/A does not; multiple retries inside A count as one encounter. Two completed helped/unsuccessful encounters suggest support, while unchecked departure and a still-open wrong attempt do not silently finalize evidence. An unavailable next band yields honest continued practice, never an invented task.
7. Calendar examples use explicit dates: first success on 2026-10-23 schedules 2026-10-26 across the London autumn DST change; independent review on 2026-10-26 schedules 2026-11-02. A due review within the same competition week is still educationally due but not a new reward opportunity. A later-week review candidate preserves canonical ID; WP05 remains the eligibility authority.
8. Muting either channel, Stop, Silence all and neutral narration leave learning/attempt/eligibility facts unchanged. Assessed-text listening qualifies reading evidence; explicit spoken hints remain sticky help. This module emits no playback or audio preference changes.

9. The DEC-024 fixture starts encounter A/episode 1 with wrong Check sequence 1 and a hint. Navigation adds no completed episode; deliberate finish adds one unsuccessful episode and no new Check. Return creates episode 2 under A; correct sequence 2 records retry/supported success with inherited help and a second completed episode, never independent first success. Duplicate finish/Check is filtered once by WP04; a zero-Check episode cannot become unsuccessful merely by finishing. Hand this exact educational expectation to WP04-04A alongside the unchanged reward expectation; numeric reward eligibility stays with WP05.

10. Reuse the existing story/transfer/resume cases with validated binding intents: omitted quest binding selects the first incomplete story row, explicit optional-as-story/mismatched quest/unknown ID is unavailable, and a requested transfer excludes its source task after source encounter compaction using permanent source completion. A bound revisit never becomes story provenance, and resuming an unresolved task from another route retains its saved provenance/help/reason. A bound request with no usable pool reports unavailable rather than selecting an unrelated task. Pure selector results do not themselves mark permanent binding completion; WP04 does so only for a later committed correct judged Check with story provenance.
