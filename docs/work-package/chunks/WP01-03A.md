## Target outcome

**Offline and optional installation disposition.** DEC-006 accepts offline play in the first slice, with optional native browser installation/fullscreen as enhancements. First use needs a successful online load. Show “Ready offline” only after the active app version's complete first-slice code/content/required art is cached and usable. An interrupted download reports “Offline preparation incomplete” with retry; online play remains available. Cache failure must not imply save failure or erase progress. With no prior cache and no connection, the browser may show its own network error; help must not promise a custom first-ever offline launch. Service workers support cached offline responses, but caches must first be populated. [MDN offline guidance](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Offline_and_background_operation).

Once ready, offline reload, all three missions, hints, scoring, local profiles, saves, leaderboard, background music and sound effects remain functional. Cache the required music/effects as project-scoped assets alongside the art; WP02 owns their free-use provenance and formats. No remote fonts, media, correctness service or account is required for that path. Speech may depend on available device voices: show written instructions always and an honest unavailable state rather than making offline read-aloud a blocker. WP03 defines reading-evidence meaning; WP04 owns settings and persisted data.

An update downloads beside the current version, remains waiting during play, and is offered as “Update on next launch”. After successful save, the player closes all game tabs/windows and reopens; do not force activation/reload mid-activity. Failed download keeps the old version usable. Keep resources for the active version until its clients are gone, never mix content versions, and remove only this app's obsolete caches. Registration scope and cache names must be restricted/namespaced to this Pages project; WP04 independently namespaces its durable store. This policy follows the lifecycle's waiting/activation and scope constraints. [Service-worker lifecycle](https://web.dev/articles/service-worker-lifecycle).

Installation uses a manifest and the browser's own supported UI; no custom install funnel, install requirement or cross-browser installation guarantee. Fullscreen is feature-detected and opt-in; denial/exit preserves state and controls. Where unavailable, play in the ordinary browser tab. Installation support varies across browsers. [MDN installability](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable).

## Produced outputs/interfaces

- Accepted WP01 producer contract under DEC-028: `registerOfflineApp({onStatus}): {retryPreparation(): Promise<void>, dispose(): void}` publishes readonly `OfflineStatus = {phase: 'unsupported' | 'preparing' | 'ready' | 'incomplete' | 'update-waiting', pageBuildId: string, activeBuildId: string | null, waitingBuildId: string | null, activeInventoryComplete: boolean, reason: string | null}`. The existing phase vocabulary remains, but waiting is not an offline-readiness assertion. Display Ready offline only when the responding active build equals pageBuildId and activeInventoryComplete is true; display the waiting update independently. Unknown/time-out status starts incomplete/preparing, never optimistically ready. `dispose` removes page listeners/subscribers, not registrations, caches or saved data. Retry rechecks/update-downloads under native lifecycle; it never calls skipWaiting.

- A request/reply MessageChannel probe addresses the specific active worker; reply carries its BUILD_ID and completeness of its injected required manifest resolved through Workbox precache keys. Verify all entries, including media, and treat a missing entry/read failure as incomplete. A waiting worker may be probed separately for waitingBuildId but cannot attest to active readiness. Reprobe on registration/controller change and return to visibility; request IDs discard stale replies. Do not infer completeness from navigator.onLine, registration success, cache names or a worker's existence.

- WP04's `UpdateReadiness`/`PreferenceStatus` supply compatible-open and pending/failed writes; accepted `flush()` acknowledges the queue's durable completion. The shell offers the managed next-launch action only when ready, tells the player to close all app clients and never forces reload. Browser/user shutdown cannot be made to save failed writes: retain the last committed state and truthful failure/retry status, and reopen through WP04 compatibility/recovery before gameplay. This does not grant the worker ownership of saves.

The accepted DEC-033 callable-lifecycle handoff is consumed through WP01-02A's shell adapter: it first awaits the registered panel's suspension, then calls WP04 flush/getUpdateReadiness using the current readTransientReadiness getter. Blocked suspension retains the view/draft and prevents the managed update offer; explicit user discard can clear the transient draft obligation but cannot clear separate failed commands/preferences. The service worker receives no panel draft or save authority. Existing pending/failed-readiness and two-client cases verify this connection, without a new release gate.

**PWA implementation choice.** Configure `injectManifest`, `srcDir: 'src'`, `filename: 'sw.ts'`, `injectRegister: false` and native explicit registration under BASE_URL. Do not use `registerType: 'autoUpdate'`, an `updateSW(true)` action, `skipWaiting`, a SKIP_WAITING message handler or `clientsClaim`; native waiting ends when old clients close. Set manifest `id`, `start_url`, `scope` and worker scope to the app path. Precache emitted HTML/JS/CSS, reviewed content, SVG/raster assets, icons and every required audio format; configure asset patterns and a measured per-file limit explicitly because plugin defaults omit non-code media and can omit large files. `check-precache.mjs` compares the built manifest with WP02's required inventory and fails for missing/oversized/out-of-scope entries. Keep old assets usable through install/waiting; remove only this app's obsolete entries on activation, using scoped Workbox cache names rather than origin-wide cleanup. A→B tests must verify no mixed build/content/audio, no deletion of another Pages app's cache, and no false Ready after interrupted installation. Worker typechecking/build and checks of `dist/` are required because development-server behaviour does not prove production offline behaviour.

Use APP_NAMESPACE plus BUILD_ID for this app's precache name. Activation cleanup matches only the exact namespace prefix and obsolete app build caches; never perform origin-wide `caches.keys()` deletion or cache/store reset. Required runtime URLs are same-origin and beneath BASE_URL. Workbox must serve the active worker's precached revision for code, content, art and audio, including stable public filenames; do not network-first those resources while A clients are open. Fetch interception is bounded to this app, and navigation fallback applies only to the app entry, not arbitrary missing asset requests.

`check-precache.mjs` consumes built `dist`, the injected manifest and WP02's release-tagged required inventory; outputs `{buildId, basePath, requiredUrls, missingUrls, oversizedUrls, outOfScopeUrls, largestAssetBytes, configuredMaxBytes, passed}`. Entries already bundled in emitted JS count by their emitted chunk, not imaginary standalone source URLs. Resolve imported assets through Vite's output mapping; normalize WP02 public paths through assetUrl. Pass requires every applicable inventory item represented and no required file above the explicitly measured maximum. The report stays outside dist. `requestFullscreen(element): Promise<'entered' | 'unavailable' | 'denied'>` is an opt-in adapter; rejection never changes progress/navigation. The shell consumes these platform outputs while WP04 retains all save-readiness authority.

Reuse [vite-plugin-pwa injectManifest](https://vite-pwa-org.netlify.app/guide/inject-manifest), [precache guidance](https://vite-pwa-org.netlify.app/guide/service-worker-precache) and [Workbox precaching](https://developer.chrome.com/docs/workbox/modules/workbox-precaching), under retained MIT notices ([plugin](https://github.com/vite-pwa/vite-plugin-pwa/blob/main/LICENSE), [Workbox](https://github.com/GoogleChrome/workbox/blob/v7/LICENSE)); release peers are checked through WP01-01A. No handwritten cache-manifest framework.

## Acceptance criteria

1. After “Ready offline”, a disconnected reload can complete the first adventure and retain progress on another reload. Interrupting preparation never produces a false ready state. Simulated unavailable cache/service worker leaves online play and truthful status; browser data eviction is not represented as guaranteed persistence.

2. Serve built candidate B over A at the isolated project-path verification origin with a saved profile and two open A clients: A remains usable, no forced reload occurs, closing only one client does not activate B, and B activates after all old clients close and a safe later launch. Failed B caching leaves A intact. After successful activation, starter progress, profile identity, score receipts and settings remain correct through WP04; incompatible data is handled by its recovery policy, never silent reset. Another project's cache/store is untouched. WP01-04A repeats the bounded case at the actual published origin; this child does not publish.

3. Installation/fullscreen absent, declined or exited causes no loss of gameplay. Read-aloud unavailable has visible text fallback. No install prompt interrupts onboarding.

4. Manifest id/start_url/scope and worker registration scope match BASE_URL. Missing/oversized/out-of-scope inventory entries fail the build check; Ready offline requires the full active-version manifest, including required audio. No remote fonts/media/judging/account in the offline gameplay path.
5. Waiting B cannot mix A/B content/audio, delete another app cache/store, bypass persisted mutes or Silence all, or create a resume burst. Failed cache preparation keeps online play truthful and is separate from save status; first-ever offline load and data eviction are never guaranteed.
6. The complete M1 inventory includes both 60–90-second PCM loops, all five effects and required art/content/icons. A missing loop or file exceeding the measured precache limit fails inventory validation; a cached shell alone cannot report ready. Readiness identifies the page and active worker version, and a waiting complete B never makes an incomplete active A appear ready. Pending/failed save or preference writes prevent the managed safe-update offer; an uncontrollable user close remains truthfully outside that guarantee.
