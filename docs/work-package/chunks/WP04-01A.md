## Produced outputs/interfaces

**State and commit design.** Use one app-scoped IndexedDB database `${appNamespace}:save`, structural version 1, one object store `records`, one `root` record. `StoredRoot = { epoch, revision, save: SaveDataV1 }`; a monotonically increasing local revision plus a fresh epoch on import/reset prevents queued old actions mutating a replacement save. `SaveDataV1` contains format/schema/content compatibility versions, fixed installation timezone, installation audio preferences, profiles keyed by immutable ID and WP05 household competition archives. Each profile contains identity/personal preferences, WP03 learning/encounter state, WP02 world/cosmetic state and WP05 reward tracks/totals/personal records. Store plain JSON-compatible data, not class instances, assets, UI components or audio nodes. Active profile is a tab's selection; every profile command captures its ID explicitly.

**Mutation DTO contract.** WP04 owns the command envelope and integration; consumers submit intent, never claimed correctness, score increments or world patches.

**Accepted binding intent/provenance (DEC-034).** WP03-01A owns LearningRouteIntent, ActivityBindingProvenance and binding resolution/selection meanings; WP03-05A/13A supply the validated delivered registry. WP04 owns the exclusive OpenEncounter payload above and the saved encounter field `bindingProvenance: ActivityBindingProvenance | null`, populated only from the validated WP03 SelectionResult and null for unbound practice. Persist it atomically with selection/task descriptor before presentation; expose the same field read-only in CommittedActivityProjection. No duplicate state-owned provenance shape or caller-supplied role is introduced.

For a fresh request, structurally validate the state payload, then call WP03-04A resolveBindingIntent with the route, current milestone, delivered bindings/catalogue and committed accessibleQuestIds/completedStoryBindingIds. Pass its ResolvedSelectionIntent unchanged into SelectionRequest with committed evidence/history/calendar and the visit suppression boolean; never maintain a second route/reason map. A missing/unavailable definition maps to invalid with the resolver reason, or unsupported for incompatible content, without encounter/attempt/award. The resolved selection must return a task within its binding pool and matching response kind; WP04 verifies that contract before persistence. WP03 owns task choice/adaptation and WP05 rechecks reward eligibility.

Optional-transfer takes only its binding ID under the WP03 route union. The producer's sourceBindingId identifies the immutable singleton M1 story anchor; permanent completedStoryBindingIds proves completion, and that retained source row's sole task ID supplies previousCanonicalQuestionId. This remains valid after reload and full source-encounter compaction. No source encounter pointer, extra history/completion-reference store or UI previous-task claim is required. The selected transfer persists its ordinary binding provenance and descriptor; resume can revalidate them from the same immutable definitions. No source-dependent M2 transfer extension is introduced. A skip makes no command/observation; unavailable optional work does not block story or ordinary practice.

For explicit resume, retrieve that existing captured-profile encounter first, revalidate its stored provenance/task against compatible definitions and reconstruct WP03's resume intent; missing/expired/cross-profile encounters fail without new selection. An unresolved canonical encounter returned by WP03 while resolving a fresh route resumes with its original provenance/reason, never the newly requested binding. The committed projection tells WP02 which work actually resumed. After that practice succeeds, a subsequent fresh required-story request may use the same canonical task under its required binding, with WP05 suppressing already-used rewards; only the newly committed required-binding success completes story progress. This preserves access and sticky attempts/help without relabelling optional/general practice.

On each judged correct Check, read the encounter's persisted provenance, validate it against the retained binding definition and apply WP03's required-activity completion condition. Only a qualifying `story` binding adds its ID to WP02-owned `WorldProgress.completedStoryBindingIds`; optional-transfer/revisit/unbound practice and FinishPractice never do. Call WP03-05A/13A areRequiredBindingsComplete for the quest/milestone/permanent set; it requires a nonempty required set and cannot pass on missing bindings. Complete the quest and grant the existing once-only WP05 quest award only when this helper is true and WP02 prerequisites hold. World completion, learning, Check receipts, points and entitlements commit in one transaction. The finite completed binding/quest sets survive encounter compaction and are validated/imported with retained compatible definitions, never reconstructed from compactable history or point totals. Exact world-field definition remains in WP02-01A.

**Accepted episode adapter (DEC-024/025).** Retain the stable encounter and its existing reward opportunity token across unsuccessful practice endings; do not allocate a replacement encounter/opportunity to reset attempts. WP04 persists `learningEpisode = { ordinal: positiveSafeInteger, status: "open" / "suspended" / "completed-success" / "completed-unsuccessful", validChecks: nonnegativeSafeInteger, firstCheckSequence: positiveSafeInteger or null, completionActionId: string or null }`. Start at ordinal 1; cumulative encounter `validChecks`, `answerHintUsed`, `workedSupportUsed`, `assessedTextReadAloud`, submission sequence and opportunity week/slot/components remain separate and sticky. The learning episode identity is the tuple `[encounterId, learningEpisodeOrdinal]`. WP03 owns the corresponding LearningObservation fields; WP02 consumes the commands below.

- `SuspendEncounter { encounterId, learningEpisodeOrdinal, responseDraft? }` validates/saves the reconstruction and marks an open episode suspended. Navigation itself never creates an observation, attempt, point or failure. Resume of suspended work reopens the same ordinal.
- `FinishPractice { encounterId, learningEpisodeOrdinal }` closes an open/suspended episode only when that episode has at least one judged Check and no success. It records a single completed-unsuccessful episode fact, without a new Check or reward component. Repeated closure of the same episode is already-applied; zero-Check finish is invalid with an ordinary Leave route available. A stale earlier ordinal cannot close the current episode.
- The exclusive `OpenEncounter { resumeEncounterId, suppressDueReviewForVisit }` form on completed-unsuccessful work increments the episode ordinal once, clears only episode-local counts/closure, and retains the same binding/canonical/encounter/opportunity and cumulative assistance/Check history. A valid correct SubmitCheck closes the episode as completed-success and completes the opportunity; later eligible review allocates a new encounter/opportunity under DEC-010.
- Consume WP03-01A's accepted DEC-025 observation union. Check eventId projects submissionId, finish eventId projects actionId; encounterCheckIndex projects cumulative checkSequence and episodeCheckIndex the current ordinal's count. Finish is completion-only without submissionId/Check indexes; correct Check carries success completion in the same event. firstCheckCorrect describes the original encounter's first Check, never the first since resumption. Pass sticky answerHintUsed/workedSupportUsed/assessedTextReadAloud and objective evidence mode. The full union remains solely in WP03-01A; this child owns persistence/commands and WP04-04A owns translation.

**Concrete root/ports.** SaveDataV1 fields are `schemaVersion`, `contentVersion`, `rewardPolicyVersion`, `installation: { timezone, audio }`, `profiles: Record<ProfileId, ProfileSave>`, and `competition: CompetitionState`. ProfileSave groups `identity`, `preferences`, `learning`, `encounters`, `world: WorldProgress`, `creative: CreativeState`, `rewards`, and `personalRecords`; use imported domain DTOs rather than a second definition. Completed quests are the source of restoration/shelf/invention facts; do not persist competing result booleans. Root tokens never enter portable save data. Freeze `ReduceCommand(root, command, context): TransitionDecision` as a synchronous port: changed `{ save, changes }`, unchanged `{ status: "already-applied" / "invalid" / "unsupported", reason }`; repository owns conflict/save-failed and token creation. `ValidateSave(candidate): ValidationResult` returns a fresh validated save or path/reason issues before write. `CommitResult` is exhaustive: committed has snapshot+changes, already-applied has current snapshot and no changes, conflict has fresh snapshot, invalid/unsupported has reason, save-failed has retryable reason and last committed snapshot when available. Typed reason codes support UI; raw exceptions/HTML are not child messages.

GetSnapshot returns the same immutable reference until a commit/refresh changes state; subscribe(listener) returns unsubscribe. `dispatch(command): Promise<CommitResult>` serializes writes, `refresh(): Promise<CommitResult>` reloads and reconciles through the same writer, `flush(): Promise<UpdateReadiness>` waits for commands/preferences and reports unsaved/failure blockers. `UpdateReadiness = { ready, pendingCommands, pendingPreferences, failedCommand, failedPreferences, unsavedTransition }`; ready is true only when all blockers are absent. WP01 consumes these ports; WP02 consumes action results, not repository internals. Missing/corrupt/unsupported storage is a separate load outcome, never a fabricated empty CommittedSnapshot. The clean first run alone initializes a root.

**Accepted transient readiness input (DEC-033).** `createStateController` requires `readTransientReadiness: () => TransientReadiness`, where the state-owned structural DTO in contracts.ts is `TransientReadiness = Readonly<{ dirty: boolean, pending: boolean, failed: boolean }>`. WP01-02A supplies one synchronous getter projecting its currently registered WP01-01A ActivePanelLifecycle status; no state/domain import is required in that early type. No active panel returns all false. The getter reads current registration state on every call; it must not capture a status snapshot at construction. WP04 performs no panel registration, draft copying or durable write for this input.

Expose `getUpdateReadiness(): UpdateReadiness` and keep `flush(): Promise<UpdateReadiness>`. Both sample the getter; unsavedTransition is dirty OR pending OR failed. Flush drains the facade's existing command/preference queues and samples again immediately before returning; it neither invokes panel suspension nor clears flags. A throwing/unavailable getter fails closed with unsavedTransition true. WP01 must first request suspension through its producer-owned lifecycle port, then call flush and honor the returned readiness. A successful flush is a current observation, never permission for forced midplay update activation.

WP02's panel retains dirty/failed status and the old draft after a failed or conflicting SaveDraft/SuspendEncounter until retry succeeds or the user explicitly chooses discard. Those draft-only command failures are returned to the panel and represented through this getter; they do not leave a second sticky failedCommand blocker after an explicit discard. Non-draft durable command failures and failed preferences remain the facade's existing blockers and cannot be dismissed by clearing panel flags. Pending writes must settle before discard/navigation can complete. WP01 changes tab-selected profile/view and tears down the old panel only after its guarded result allows it; no durable activeProfile field is added. Registration identity/cleanup remains WP01-owned: stale unregister/status/async completion from an older panel must not clear or replace a newer panel's readiness. State reads the current getter result only.

**Accepted committed activity read handoff (DEC-032).** WP04-04A implements the pure export `selectCommittedActivity(snapshot: CommittedSnapshot, catalogue: readonly TaskDefinition[], key: { profileId: ProfileId, encounterId: string }): ActivityProjectionResult` in `src/state/controller.ts`. It reads an explicit acknowledged snapshot; it never dispatches, obtains time, grades, allocates IDs or changes rewards. WP02-06A/10A call it after acknowledgement and on snapshot changes/reload, then use their own toActivityTaskView adapter. This is one selector over existing data, not another store or controller service.

`ActivityProjectionResult` is `{ status: "ready", activity: CommittedActivityProjection }` or `{ status: "unavailable", reason: "profile-missing" / "encounter-expired" / "content-unavailable", token: SaveToken }`. Ready projection fields are `token`, `profileId`, `encounterId`, `learningEpisodeOrdinal`, `episodeStatus`, `nextCheckSequence`, `task: Readonly<TaskDefinition>`, `responseDraft: ActivityResponse | null`, `lastEvaluation: Extract<EvaluationResult, { status: "judged" }> | null`, `lastCheck: { submissionId, checkSequence, learningEpisodeOrdinal, response: ActivityResponse } | null`, `revealedAssistanceIds: readonly string[]`, `bindingProvenance: ActivityBindingProvenance | null`, original WP03 `selectionReason`, `familiar`, `reviewReference`, and `rewardDisplay: { eligibility: EligibilityResult, earningWeek: WeekKey | null, slot: number | null, components: RewardOpportunity["components"] | null, earningWeekOpen: boolean, lastCommittedDelta: ScoreDelta | null }`. Import all reward subtypes from WP05-01A. Eligibility/reason and component facts are stored WP05 outputs; earningWeekOpen compares the stored earningWeek with the snapshot's active competition week, false for null, never a fresh clock read. No UI recomputation of eligibility, points or first-attempt status is required. Null earningWeek/slot before the first valid Check means unbound, not cap reached. A practice-only selection is labelled from its stored WP05 classification. Presentation of lastCommittedDelta after reload is informational, never a celebration trigger.

Persist on each retained encounter only the bounded reconstruction/read facts: canonical descriptor plus `taskContentRevision`, nullable `responseDraft`, `revealedAssistanceIds`, latest WP05 classification and `lastCommittedCheck` (null initially, otherwise submitted response, submission/sequence/episode identity, the actual judged EvaluationResult and actual ScoreDelta). A valid Check atomically replaces that single last-check record, updates the saved draft to its submitted response and commits learning/reward/world facts. Invalid/incomplete/save-failed Checks never replace it. RecordAssistance adds only producer-approved assistance IDs after commit; routine instruction narration adds none. SaveDraft/Suspend may replace a saved draft with a validated partial response without changing lastEvaluation, so lastCheck explicitly identifies the response/episode to which feedback belongs. WP04-03A validates these bounded fields and references through the same save contract; it does not reconstruct an event log.

Resolve task from the locally supplied approved catalogue by canonical descriptor/identity and the exact retained content revision, including explicitly retained compatible task records. Store neither a duplicate full TaskDefinition nor assets in the save. If that approved record/revision or a revealed assistance ID cannot be resolved, return content-unavailable and preserve all saved data; do not silently grade against a changed task, reveal withheld material, clear progress or manufacture a default question. LastEvaluation is the stored actual judged result, never reevaluated on a read or reload. LastCheck and lastEvaluation are both null before the first committed judged Check and remain attributed to their original episode after unsuccessful finish/resume; WP02 must not label old feedback as a judgement of a newly edited draft.

Null responseDraft means no deliberate draft or judged Check has yet been saved. WP02 initializes its transient empty controls using task.responseSpec (empty planks, null counts/slots or empty permitted mappings as appropriate); the selector does not invent a scored/default answer. Unsaved in-view edits stay local until SaveDraft/Suspend/Check, and a fresh projection must not overwrite a dirty draft bound to the same profile/epoch/encounter/episode. Missing profile or compacted/unknown encounter returns the unavailable tag rather than substituting another active profile. Celebration continues to depend solely on a new committed CommitResult.changes; a selector result never earns or replays anything.
