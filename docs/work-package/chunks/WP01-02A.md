## Target outcome

One semantic DOM/SVG application supports the [WP01-01A matrix](WP01-01A.md#target-outcome) between supported viewport sizes and both tablet orientations. Portrait rearranges controls; no forced fullscreen/orientation. WP01 hosts exported panels and quick audio controls; owners retain domain behaviour.

**Required audio lifecycle (DEC-004).** WP01 hosts WP02's quick audio panel on every gameplay screen: explicit Enable sound, independent music/effects mute and volume, persisted Silence all, and immediately reachable read-aloud Stop. First visit stays silent until Enable sound; an unrelated first click is insufficient. Initial enabled levels are 25% music/50% effects. WP04 loads installation-wide preferences before any playback; failed reads stay silent. Profile changes cannot restore a louder setting. Silence all stops music, effects and speech, survives visits/updates, and needs an explicit exit; narration and sliders cannot exit it. Sliders never implicitly unmute. Immediate live silence survives failed preference writes with truthful persistence status. Every new page still obeys browser gesture/autoplay restrictions and handles blocked playback without retry storms or blocking play. [MDN autoplay guidance](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay).

Pause music and stop transient effects/read-aloud when the game becomes hidden or paused. Return/resume restores only permitted music at its current preference; do not replay queued effects or narration. If the browser needs another gesture, expose an enable/resume action. Visibility can be observed through the [Page Visibility API](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API); WP02 owns the actual audio controller and mix. Navigation, profile changes and app updates never bypass mute. The complete game remains understandable with all sound off.

## Produced outputs/interfaces

- Consume WP01-01A's `AppView`/`NavigationPort`; do not duplicate their definition. WP02 owns the current scene/activity adapter, WP04 profile/adult panels, WP05 Hall/personal-history panels. The shell supplies a shared header/main/help and focus return, not a replacement domain screen. Returning restores durable encounter facts through WP04. Explicit leave asks WP02 to save its canonical draft through WP04 before navigation; failure retains the current view/draft and offers retry. Browser shutdown cannot promise saving uncommitted drafts. Normal navigation/visibility changes never dispatch deliberate finish-practice (DEC-024).

**Selected profile (Stage 10 P2 correction).** `AppShell` owns tab-transient `selectedProfileId: ProfileId | null`, importing the ID type from its existing producer; selection is not added to AppView or the durable save. Supply it to WP04 ProfileChooser/AdultArea and pass a non-null validated `selectedProfileId` explicitly to WP02 AdventureView and its M2 successor. With null or an ID absent from the latest committed snapshot, show the chooser instead of mounting an adventure for an inferred profile. `onSelectProfile(nextProfileId)` requests the same leave guard as navigation; only a ready result changes the selected ID and mounts the new adventure. Retain the old selection/view/draft on blocked suspension. Validate the target ID again after awaiting the guard. Capture old registration token, selected profile and save epoch when the transition starts; ignore late completion if any has changed. A save replacement/reset invalidates the old binding; never migrate its draft or queued callback into the replacement household. Missing/deleted profiles return to chooser without fabricating new ones.

**Callable active-panel guard.** Supply `activePanelHost: ActivePanelHost` to WP02 AdventureView/M2 adapters, importing the sole definition from [WP01-01A](WP01-01A.md#produced-outputsinterfaces). QuestActivity registers its implemented ActivePanelLifecycle while active. The shell's registry allocates registration tokens, owns the subscription and ignores stale callbacks/unregister closures. A navigation/profile-change request captures the current registration and serializes one leave operation; keep the old panel mounted while its `suspend()` runs. Block further navigation/switch requests while pending rather than replaying a stale destination later. Recheck registration/profile/epoch and panel status after ready; only then apply the requested destination. A blocked result or rejected promise retains the old panel, focusable failure message and Retry/Stay/Discard-draft actions. Retry calls that same registered panel's suspend again; explicit discard calls discardDraft and leaves only on ready with no pending work. Neither cleanup nor a failed promise implies discard. Stop speech/cancel active gesture through producer teardown only once the transition is permitted; immediate Silence all remains available throughout.

**Readiness consumer adapter.** Supply WP04's `createStateController` with its required `readTransientReadiness: () => TransientReadiness`, importing the structural result from [WP04-01A](WP04-01A.md#produced-outputsinterfaces). The getter reads the current registration on every call: project panel dirty; panel pending OR guard in flight; panel failed OR unresolved failed transition. No active panel and no unresolved transition yields all false. Do not capture the mount-time status. Panel notifications rerender shell save/update controls, which call the facade's `getUpdateReadiness()`; `flush()` drains the existing durable queues and samples the getter again. No durable field, copied draft or second state controller is added. Update preparation first uses the same panel suspension guard, then awaits flush/readiness; dirty/failed work must not be erased by merely unregistering a panel. Explicit discard clears only the panel's transient obligation; independent command/preference failures remain WP04 blockers. This path never activates or reloads a waiting worker during play.

- `createAppRuntime` opens WP04's `openSaveRepository`, creates its sole `createStateController` with WP03 evaluation/selection and WP05 reward/calendar dependencies, and creates WP02's sole `createAudioController`. `StateControllerProvider` supplies this controller through React context; `useGameSnapshot` uses `useSyncExternalStore`. Consume DEC-017's accepted `getSnapshot()` (readonly/stable until change), unsubscribe-returning `subscribe(listener)`, `dispatch`, `refresh` and durable `flush()`/readiness; no second GameRuntime/store. Shared mutation/save DTOs live in `src/state/contracts.ts`; domain DTOs stay with their owners. Match WP04 `CommitResult` statuses: committed, already-applied, invalid, conflict, save-failed, unsupported. Only a committed result emits a fresh celebration.

- Use WP02's `createAudioController({assetResolver, persistPreferences, speechAdapter})`, `src/audio/AudioControls.tsx` and `StopReading`. Shell integration forwards `setVisible`, explicit `enableSoundFromGesture`, `exitSilenceAllFromGesture`, `stopReading` and `dispose`; pause behaves as hidden, without changing durable preferences. Controller subscription feeds the panel. Load WP04's `InstallationAudioPreferences = {soundEnabled, silenceAll, music:{muted,volume}, effects:{muted,volume}}` before any audio. WP02 owns the synchronous live playback gate; WP04 alone owns requested generations, coalescing, cross-tab propagation and durable preference writes. Navigation stops speech, hide stops effects/speech and pauses music, and a persisted Silence all cannot be exited by unrelated gestures, sliders or narration.

Use accepted DEC-017/020 names directly: DTOs live in their producer modules; contract changes are proposals to Controller/owner rather than silent new interfaces. Bootstrap waits for preferences/read-failed silence before playback; no competing GameRuntime/store.

`createAppRuntime` returns the sole state/audio instances plus idempotent `dispose(): void`; initialize outside view routing. `src/platform/lifecycle.ts` attaches visibility/pagehide listeners once, forwards current visibility/paused state to audio and returns an unsubscribe function. On route/profile change stop speech before mounting the next panel; never replay previously queued narration/effects. `useGameSnapshot` reads WP04's stable snapshot and subscribes with its returned unsubscribe. Only `committed` plus new producer-supplied presentation changes can celebrate; `already-applied` restores state without a new celebration.

**Accepted consumer adapter (DEC-026):** bind WP02-05A's `persistPreferences(change: AudioPreferenceIntent)` to WP04-05A's `setAudioPreferences(intent)`. ## Acceptance criteria

1. Shell checks pass at every D1–T2 viewport with completed producer panels; WP06 later owns full published journeys and matrix release acceptance. Essential controls, instructions, feedback and progress are neither clipped nor hidden by overlays; portrait rearranges the interface rather than shrinking all controls. Rotation preserves the current answer and attempts without accidental submission. Shorter screens may scroll vertically; no required text needs horizontal scrolling.

2. All shell functionality works by keyboard with visible, unobscured focus and no trap; dialogs return focus to their opener. Normal text contrast is at least 4.5:1, large text 3:1, and meaningful control boundaries 3:1. Text can enlarge to 200% without loss of action/content. Meaning is not colour-only. These targets apply the relevant [WCAG 2.2 criteria](https://www.w3.org/TR/WCAG22/), not a claim of complete certification.

3. Project-specific comfort targets: instructional/body text starts at 18 CSS px; child-facing hit areas are at least 44 × 44 CSS px, including tap alternatives for small puzzle objects. Every drag action has a tap/select-then-place and keyboard route through WP02. Live DOM text and semantic controls accompany SVG scenery. Reduced motion removes nonessential movement, and no shell operation requires audio or timed input. WP02 coordinates this contract under GAP-009/DEC-005.

4. Shell loads audio through the project asset resolver; full offline inventory/update proof belongs to WP01-03A. First visit needs explicit Enable sound after preference readiness; unrelated clicks never enable it. Both mutes, both zero-volume settings and persisted Silence all remain effective through scene/profile changes, hidden/resume and reload; the next child carries this invariant through A→B. Sliders/narration never unmute or exit Silence all. Quick controls are keyboard/touch accessible in one panel-opening action from every gameplay screen; read-aloud Stop is visible while speaking. Hiding stops narration/effects and pauses music; resuming creates no duplicated loops or queued burst. Audio denial/storage failure preserves immediate live silence and continued play.

5. Runtime composition uses `createStateController` and accepted CommitResult vocabulary; committed snapshots alone publish durable consequences. Profile changes cannot restore louder audio, and failed reads start silent. Available/unavailable local read-aloud remains visibly honest; written text is always usable.
6. Repeated view mount/unmount and development remount leave exactly one live state subscription/audio controller per application runtime; disposed callbacks cannot play sound or publish stale state. Mute/Silence all applied while an asset decode or resume is pending still governs its completion. A delayed failed preference write never restores louder state. Test these through producer ports, without creating a shell-owned audio player.
7. Leaving an activity saves its producer-owned draft or visibly retains it on failure; switching views never invokes finish-practice, resets attempts/help or revives first-attempt reward eligibility. Deliberate finish-practice remains the WP02→WP04 command path. A failed runtime open exposes WP04 recovery/retry and text-only silent UI; it does not instantiate a replacement empty store.
8. With two real local profiles, chooser selection reaches AdventureView/M2 through selectedProfileId. A pending/failed old-profile suspension retains the old selection and draft; retry or explicit discard permits switching without transferring attempt/help/reward state. A stale completion after epoch replacement cannot render into the new profile. Null/deleted selection produces the chooser.
9. The registered panel's initial and changed dirty/pending/failed flags reach WP04 transient readiness; successful suspension or explicit safe discard clears only that transient obligation. Late unregister/notification from an old registration cannot clear a newer panel or its blocker. A failed suspension prevents both view change and managed update readiness. Reuse the existing shell/failure/epoch cases for these checks; no separate framework or release gate.
