**Accepted quest binding contract (DEC-034; Stage 10 P2 correction).** Define `ActivityBindingId = string`, `QuestActivityBinding`, `ActivityBindingProvenance`, `LearningRouteIntent`, `ResolvedSelectionIntent` and `BindingResolution` in this learning-owned contract module. Quest identifiers here are plain validated strings, with no import of the later WP02 module. WP02-01A supplies the actual quest registry to downstream validation; early DTO construction still follows DEC-022. Exact persisted WorldProgress fields and OpenEncounter command envelopes remain with WP02/WP04 respectively.

`QuestActivityBinding = { bindingId: ActivityBindingId, questId: string, availability: 'M1' | 'M2', role: 'story' | 'optional-transfer' | 'revisit', skillId: SkillId, taskIds: readonly string[], mechanic, responseKind: ActivityResponse['kind'], sourceBindingId: ActivityBindingId | null }`. `mechanic` retains the six existing values (`drag`, `matching`, `sequencing`, `sorting`, `object-manipulation`, `consequential-selection`). Every task ID resolves to approved content with this primary skill and response kind. A binding's role/quest/skill/meaning is immutable once released. The array order of story rows gives the default within-quest offer order; explicit selection of another incomplete story row in that available quest is also permitted. `story` means required; it is not an editable UI flag. A required binding succeeds after one correct judged Check on a task selected and persisted under that binding, including supported/retry success. It never requires clearing the whole task pool.

`ActivityBindingProvenance = { bindingId: ActivityBindingId, questId: string, role: QuestActivityBinding['role'] }` is derived from the validated binding, never copied from caller claims. WP04 persists it with the selected canonical descriptor and original selection reason; unbound general practice has null provenance. A Check cannot substitute bindingId, questId or role. Resume restores this provenance and its retained task, independently of the current screen. A free-practice encounter cannot be relabelled required story work on return; opening required work after practice still obeys existing sticky canonical attempts/help and reward rules.

`LearningRouteIntent` is the readonly union below, carried as fresh selection intent inside WP04's own OpenEncounter payload. The local owner defines the final command envelope and mutually exclusive resume form; a resume does not accept a replacement route/binding.

| kind | Fields | Validation / resolution |
|---|---|---|
| `quest` | `questId: string, bindingId?: ActivityBindingId` | Quest must be available in the current milestone and its world prerequisites met. With an ID, require an incomplete story row of that exact quest; without one, choose its first incomplete story row in catalogue order. Completed/optional/mismatched rows cannot be opened as required work; use their explicit practice route instead. Resolve to story-anchor with validated binding provenance. |
| `optional-transfer` | `bindingId: ActivityBindingId` | Require an available optional-transfer row and permanent completion of its sourceBindingId. Its source must be a story row for the same quest/skill with exactly one fixed task: the existing M1 anchor. Derive previousCanonicalQuestionId from that source row, not a UI-supplied answer or compactable encounter. Resolve to transfer and exclude that source task. No M2 transfer extension is introduced. |
| `revisit` | `bindingId: ActivityBindingId` | Require an available revisit row belonging to an already accessible quest. Resolve to adaptive-practice within that row's task pool; provenance remains revisit even if it reuses a story task. It cannot complete required work. |
| `practice` | `skillId?: SkillId, mode: 'suggested' / 'easier' / 'repeat'` | Require a delivered skill when supplied; otherwise use the first delivered skill in registry order after optional due-review selection. Resolve respectively to adaptive-practice, child-easier or repeat-practice with null binding/provenance. UI supplies no canonical task, answer, eligibility or completion fact. |

`ResolvedSelectionIntent = { kind: 'story-anchor' | 'transfer' | 'adaptive-practice' | 'child-easier' | 'repeat-practice' | 'resume', skillId: SkillId | null, binding: QuestActivityBinding | null, provenance: ActivityBindingProvenance | null, previousCanonicalQuestionId: string | null }`. Bindings restrict selection to their listed task pool. For required M2 work, story-anchor denotes required story provenance, while its pool may offer a suitable band rather than a single fixed introductory anchor. Due review may be offered only for unbound suggested practice; it cannot silently replace a specifically requested story/transfer/revisit with a different task or provenance. Resume uses the committed encounter's original provenance/reason and no newly selected task.

`BindingResolution = { status: 'resolved', intent: ResolvedSelectionIntent } | { status: 'unavailable', reason: 'unknown-binding' | 'route-mismatch' | 'milestone-unavailable' | 'quest-unavailable' | 'already-completed' | 'source-incomplete' | 'invalid-binding' | 'no-suitable-task' }`. Pure resolver inputs contain the declared route, milestone, bindings, delivered catalogue, accessibleQuestIds and completedStoryBindingIds; the last two are WP04-supplied projections of world facts, not UI assertions. accessibleQuestIds includes currently unlocked and already completed quests; completedStoryBindingIds is the permanent WP02 WorldProgress set, never reconstructed from encounter receipts. WP04 adapts unavailable results to its existing invalid/unavailable handling without an attempt, failure observation or award.

Every story binding is required for its quest and only story bindings count toward completion. `sourceBindingId` is non-null only for optional-transfer; these rows are M1 anchor transfers. Revisit/story rows use null. An optional transfer's task pool excludes its source canonical ID and is nonempty. Source links stay within the same quest/skill and cannot form a cycle. Task lists/IDs are unique and consistent with the approved catalogue. M1 catalogue includes only delivered M1 rows; M2 retains those unchanged and adds M2 rows. No added M2 requirement is attached retrospectively to Q1–Q3. Unknown or malformed bindings are content faults, not learner wrongness.

Consumers: WP03-04A owns pure route resolution/selection; WP03-05A and WP03-13A own the validated binding catalogue and required-set helpers. WP04-01A/04A own OpenEncounter validation, immutable saved provenance and atomic success application; WP04-07A preserves this through M2. WP02-01A owns the permanent binding-completion field in WorldProgress; WP02-06A/10A request only the declared route intent. DEC-034 accepts these exact producer definitions and their state/world consumers. The [independent affected recheck is complete](../evidence/STAGE10-RECHECK.md); no new edge or framework is proposed.

- `TaskDescriptor = { familyId, equivalenceVersion, authoredKey: string | null, parameters }`: `parameters` is a sorted-key record of meaningful finite integer/string values, never a seed. An authored item has an authored key; generated items have the complete reconstructible parameter tuple. `canonicalQuestionId(descriptor): string` preserves the three specified anchor strings and uses an unambiguous family-specific encoding for other descriptors. `contentRevision` belongs to the task record and is excluded from identity.
- `TaskDefinition` names `canonicalQuestionId, descriptor, contentRevision, skillId, objectiveId, band, contextualSkillIds, curriculum: { sourceUrl, section, programmeBand }, demandRationale, instructionText, assessedText, stimulus?, responseSpec, answerRule, explanation, hints, workedSupport, narration, review`. `stimulus?: TaskStimulus | null` is absent/null for text-only tasks and present when an assessed representation is supplied. `hints` is a two-element tuple with stable hint IDs. `review` contains status (`approved` or `withheld`), reviewer identity, rationale and evidence reference. `narration` contains safe neutral text and whether assessed text may be spoken before Check; it never contains a playback callback. Only approved tasks enter the delivered catalogue. No state/reward/experience types are imported.
- `ActivityResponse` uses `kind` and semantic values: `bridge { planks: readonly number[] }`; `merchant { apples: number | null, pears: number | null }`; `punctuation { slots: Record<string, string | null> }`; `choice { choices: Record<string, string | null> }` (one named slot normally, inference and clue slots when required); `sequence { orderedIds: readonly string[] }`; `sorting { groups: Record<string, string | null> }`; `matching { pairs: Record<string, string | null> }`; `quantity { values: Record<string, { numerator: number, denominator: number, unit: string } | null> }`; `clock { minutes: number | null }`. `responseSpec` gives allowed IDs, required slots, cardinality, integer bounds, units and any denominator/form requirement for that task. Finite choice forms cover speech editing and shape/turn options. Exact quantity rationals also represent scaled decimals/pence. WP02 owns the widget-to-response adapters, including display scale and accessible labels.
- Structural validation takes `unknown`: wrong discriminant/type, unknown IDs, duplicate tiles or forbidden values are `invalid-response`; a well-formed permitted partial draft is `incomplete`; only a complete in-domain response is `judged`. Invalid task definitions are `unavailable-content`. `EvaluationResult` is tagged by `status`; judged fields are `correct, canonicalQuestionId, skillId, objectiveId, band, feedback: { explanation, issues }`, where each issue names a known slot/constraint and an observed mismatch. No judged result carries points or claims diagnosis.
- `TaskFamilyManifest = { moduleId, familyIds, taskIds, retainedTaskIds, domainDescription, reviewEvidenceRef, cases }`; `taskIds` lists new records from this module and `retainedTaskIds` references unchanged starter records for inventory/compatibility only. Each case names `caseId, canonicalQuestionId, response, expectedStatus, expectedCorrect?, expectedIssueCodes`. It is a small export for assembly/review, not a plugin registry. All family evaluators take `(task: TaskDefinition, response: unknown): EvaluationResult`. Owning-family `validate…Task(task: TaskDefinition): readonly ContentIssue[]` validates domain reachability/record structure using the declared family and `ContentIssue { canonicalQuestionId, field, code, detail }`; implementation stays in the owning family, not a universal expression engine.

**Accepted lifecycle adapter (DEC-024/025).** Retain WP04's durable `encounterId` and WP05's linked `opportunityId`, with a monotonically numbered learning episode inside it. [WP04-01A](WP04-01A.md) alone defines the persisted learningEpisode fields and SubmitCheck/SuspendEncounter/FinishPractice/OpenEncounter command shapes. WP03 imports no state type; its observation uses the episode identity tuple `(encounterId, learningEpisodeOrdinal)`. Suspension records no observation. Deliberate finish closes an open/suspended episode only after a judged unsuccessful Check and no success; its event identity comes from the existing actionId envelope. Repeated closure is already-applied, zero-Check finish is invalid without learning/reward change, and a stale ordinal cannot close a newly resumed episode. Return after unsuccessful finish advances the episode ordinal; return after suspension retains it. Both preserve canonical identity, cumulative Check sequence, inherited help/attempts, opportunity/earning week/slot and receipts.

`LearningObservation` common fields are `eventId, profileId, encounterId, learningEpisodeOrdinal, canonicalQuestionId, skillId, objectiveId, band, selectionReason, localDate, competitionWeekId, familiar, reviewReference, assistance`. The union has:

- `kind: check` with `submissionId, episodeCheckIndex, encounterCheckIndex, firstCheckCorrect, correct, issues, episodeCompletion: null | success`. Both indexes are one-based valid-Check counts; `encounterCheckIndex` directly projects WP04's cumulative `checkSequence` and never resets at an episode boundary. `episodeCheckIndex` is the count within the current ordinal. Wrong Checks have null completion; a correct Check carries success completion in the same observation, not a second event. `firstCheckCorrect` describes the retained encounter's original first Check, never the first since resumption.
- `kind: finished-unsuccessfully` with `episodeCompletion: deliberate-unsuccessful` and no `submissionId` or Check indexes. It completes the existing Check-bearing episode accumulator without adding another attempt. `eventId` projects the WP04 envelope action ID; Check event IDs project submission IDs.

`assistance` contains sticky `answerHintUsed, workedSupportUsed, assessedTextReadAloud` and objective-specific `evidenceMode: independent | listening-supported | mixed`. WP04 constructs observations from committed facts and applies each accepted event once; callers cannot assert independence or fabricate a judged result. WP03's completion window is keyed by `(encounterId, learningEpisodeOrdinal)` and contains only Check-bearing outcomes; it allocates no IDs and cannot complete a reward opportunity. Successful continuation after earlier unsuccessful closure remains retry/supported evidence, even when the new episode succeeds on its first local Check.
