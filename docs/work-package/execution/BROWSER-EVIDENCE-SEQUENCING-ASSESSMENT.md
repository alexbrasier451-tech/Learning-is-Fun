# Browser-evidence sequencing assessment

9 October 2026. Astra/high bounded task assessment, report-only. No amendment is in force and no dependency is released by this report. Controller decides whether further independently reviewed package amendment is warranted.

## Finding

The current package does **not** authorize final assembly/candidate publication from component technical handoffs while their expressly required early-host browser observations remain pending. It distinguishes candidate publication from M1 acceptance, but does not define a separate component handoff that releases those composition dependencies before component completion. Its explicit frozen-contract construction permissions do not include final adventure/shell composition.

The available evidence establishes a **legitimate external browser-capability blocker**, not yet a demonstrated materially wrong or inconsistent sequencing definition. Unlike the earlier multi-binding defect, the required browser cases are valid and executable on a capable host; they do not contradict the released product contract. The package deliberately specifies early-host evidence before composition, followed by published evidence. Stable interfaces and a desire to produce a reviewable candidate do not alone show that this order is defective. I do not recommend authoring an amendment under the package-defect route on the present evidence.

There is also no current actual-domain handoff proving that browser availability is the only remaining component blocker. The independently reviewed Hall is technically ready within its frozen read-model scope; its real-facade closure/refresh proof is still outstanding. This assessment must not promote that narrower result to the hypothetical completed actual-domain boundary in the question.

## Why published evidence is not automatically identical component evidence

The ordinary published journeys do not enumerate every early-host state. Hall includes empty/unscored/single/tied/capped/clock/omitted-history/refresh-failure displays. Adult includes the exact supplied learning-summary history, cancellation/failure/confirmation and focus outcomes. Some controlled published boundary setups already exist, but their existence does not establish all those states and expected values through normal supported routes.

The declared browser scope also differs: Hall explicitly puts its finite state set in D1/T1; D3's shared matrix obligation is bounded Firefox smoke, not a new requirement to run every Hall fixture in Firefox. Preserve the exact relevant-view checks rather than inflating them. [WP01-01A's matrix](../chunks/WP01-01A.md#target-outcome) remains authoritative for browser, viewport and input.

Early-host fixture entries are expressly excluded from dist/precache under DEC-027. They cannot simply be shipped with the candidate to claim equivalent published coverage. Real supported backup imports/clock controls may establish some states, but arbitrary production state mutation, private fixture controls or a second UI are not authorized substitutes. Where identical scope cannot be exercised through the actual published application, the original host case remains necessary.

WP06-01A additionally requires a usable observation/choice/resume route proved in an early-host rehearsal. An eventual fixed published script would not satisfy that requirement. Its missing D1 evidence is not evidence that the package incorrectly requires publication first: its host already exists, and launch capability is the external blocker.

## Controller disposition

The smallest supported clarification is an accurate status interpretation, with no rule change:

> A technical deliverable may pass independent review within its recorded scope while its child remains incomplete. Continue only work already permitted by the dependency/concurrency contract. Do not treat technical readiness as completion or release an edge requiring a completed panel. WP06-01A's blocked D1 rehearsal blocks its tooling completion and the corresponding downstream observations; it is not a direct prerequisite for WP01-04A publication. Required browser and acoustic observations retain their owners and acceptance gates.

This interpretation allows existing frozen-port component work and read-only publication preparation; it does not grant early final assembly or deployment. Keep the pending facade corrections/acceptance, actual-domain Hall/adult integration, audio work and their required independent checks progressing according to their own authority. Nothing in this report decides their status.

If Controller elects to revisit the sequencing policy after actual-domain evidence is available, it would be a substantive bounded change, not an already-permitted reading of “candidate readiness.” A defensible amendment would have to identify the exact otherwise-complete technical handoff, each affected composition/publication edge and each unchanged browser criterion; specify where the original host observations remain or demonstrate a scope-equivalent published route; retain whole-child and release acceptance pending those observations; and account for adventure/shell/platform browser obligations as well as Hall/adult. A blanket “all unavailable component checks move to WP06” sentence would be insufficient. Those are limits on an optional future assessment, not new tests/gates or an amendment proposed for acceptance now.
